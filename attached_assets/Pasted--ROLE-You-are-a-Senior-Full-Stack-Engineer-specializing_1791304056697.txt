# PART 2: TEAM LOGIN, ONE CODE, ONE CAPTAIN, ONE DEVICE

## 2.1 Rules
- Each team has **one access code** generated by the admin. No team-name or passcode field; the code alone identifies the team.
- **Only the team captain logs in.** One person, one device at a time. Teammates follow the captain ("Keep this phone with your team").
- A second device with the same code is refused. The same device always resumes silently.

## 2.2 Code format
- 8 characters in two groups (e.g. `K7MQ-4XPD`), alphabet without look-alikes (no `0 O 1 I L`), generated with `crypto.randomInt`.
- Case-insensitive; ignore spaces and dashes; auto-uppercase and auto-insert the dash while typing.
- Stored **hashed** (bcrypt or SHA-256 + pepper) plus a non-secret `codeHint` (first 2 chars). Full code shown to admins only at generation/regeneration.

## 2.3 Flow (one screen, minimal taps)
1. Single large auto-focused code field (`autocapitalize="characters"`, `autocomplete="one-time-code"`), **auto-submits at the 8th character** (keep a fallback button).
2. **Unclaimed code:** one extra field, "Captain's name", asked once. Server binds the team to this device.
3. **Same device returning** (cookie + stored deviceId match): skip everything, resume the game, even after refresh/crash/closed tab. Rolling session valid for the event (24 h, refreshed on activity).
4. **Different device, code already claimed:** "This team's captain is already signed in on another phone. Only one phone per team. If that phone is lost or dead, ask an organiser to release the login." Never reveal the captain's name or team data. Wrong code: "That code isn't recognised. Check it against your slip."
5. After login the same card flips to **"Set sail"**: one big button that in a single user gesture runs: unlock AudioContext (play silent buffer) → request geolocation → iOS `DeviceOrientationEvent.requestPermission()` → Screen Wake Lock → `POST /api/game/start`. Show a ruled checklist inked off as each step succeeds. Any denial shows the fix-it note and a "Try again" button that resets nothing.

## 2.4 Server enforcement
- `Team` fields: `accessCodeHash`, `codeHint`, `leaderName?`, `sessionId?`, `deviceId?`, `claimedAt?`, `lastLoginAt?`, `userAgent?`. No old passcode field.
- `POST /api/auth/team/claim { code, deviceId, leaderName? }` returns `ok | needs_leader_name | already_claimed | invalid`. Client creates `deviceId` once (UUID in localStorage).
- JWT (httpOnly, secure, sameSite cookie) holds `teamId` and `sid`. **Every REST request and socket handshake verifies `sid` against `Team.sessionId`.** Mismatch = 401 and forced sign-out.
- **One socket per team:** a new valid socket disconnects the old one; stale `sid` is rejected.
- Rate limits: 10 code attempts per IP per 5 min, 20 per code per hour, with "Too many tries, wait a minute." Log failed attempts for admins.
- Progress, route and completions are unaffected by logout/login or release.

## 2.5 Admin login controls (Team Manager)
Per team: code hint, login status (Unclaimed / Claimed by captain / last seen), device summary ("Chrome on Android"), claimed time. Buttons:
- **Release login:** clears session/device/captain, kills their socket, keeps progress.
- **Regenerate code:** new code shown once (copyable), invalidates old code and session.
- **Bulk create/generate:** paste a list of team names, all codes generated at once.
- **Print code slips:** print stylesheet, 8 per page, each a small torn parchment ticket with logo, event name, `segment`, team name, big Plex Mono code, and "Captain only. One phone per team. Don't share this code."
- **Download codes as CSV.** Confirmation dialogs and toasts. Admin activity log for releases and failed attempts.

# PART 4: GAME LOGIC (server is the source of truth)
- **Route generation:** on first start, per-team shuffled route (Fisher-Yates with `crypto.randomInt`) in one DB transaction. Idempotent: never reshuffles. Best effort: no two teams share the same first checkpoint (when teams ≤ checkpoints) and no identical full orders.
- **Capture (server-side Haversine):** distance to the team's CURRENT checkpoint only. Capture when `distance <= radiusM` AND `accuracy <= max(radiusM, 40)`. Require 2 consecutive qualifying pings, or 1 ping plus a client "arrive" event the server re-validates. Defaults suit campus tree cover: radius 30 m, both editable in admin "Game Settings".
- On capture: write `Completion`, increment `currentIndex`, emit `checkpoint:captured` to the team (with NEXT target coordinates) and `admin:team:update` + `admin:completion:new` to admins. Last checkpoint sets FINISHED and emits `voyage:complete`. Never double-award.
- **Never send future checkpoint coordinates to a team client.**
- **Anti-cheat:** flag (don't drop) pings implying > 12 m/s, accuracy exactly 0, or identical repeating coordinates; flags show on the admin dashboard.
- **Admin edits mid-game:** soft-delete via `isActive`; if a team's current checkpoint is deactivated, auto-advance and notify them.
- **Event controls:** admin Start / Pause / End. While not live, teams see the waiting screen and captures are rejected.

# PART 5: REST + SOCKET CONTRACT
**REST:** `POST /api/auth/team/claim`, `POST /api/auth/admin/login`, `POST /api/auth/logout`, `GET /api/auth/me`; `POST /api/game/start` (idempotent), `GET /api/game/state`; admin CRUD `/api/admin/checkpoints` and `/api/admin/teams`; `POST /api/admin/teams/:id/{reset|release|regenerate-code}`; `POST /api/admin/teams/bulk`; `GET /api/admin/overview`; `GET/PATCH /api/admin/settings`; `POST /api/admin/event/{start|pause|end}`; `GET /api/admin/export.csv`; `GET /api/admin/codes.csv`; `GET /api/admin/logs`.
**Socket:** JWT in handshake; teams join `team:{id}`, admins join `admins`.
- Client → Server: `location:update {lat,lng,accuracy,heading?,ts}` (max 1 per 3 s per socket)
- Server → Team: `checkpoint:captured`, `target:update`, `voyage:complete`, `event:status`, `error:flagged`, `session:revoked`
- Server → Admins: `admin:snapshot`, `admin:team:update`, `admin:completion:new`
- On reconnect the client re-syncs from `/api/game/state`.

# PART 6: TEAM VIEW BEHAVIOR
**6.1 The 39-Second Oracle:** continuous `watchPosition` (`enableHighAccuracy: true`, `maximumAge: 0`, `timeout: 20000`) writes to a ref, not React state. One 39,000 ms cycle: at each tick snapshot the latest position, compute bearing and distance, swing the needle. UI is deliberately frozen in between. The countdown is driven by `performance.now()`, not an incrementing `setInterval`, so it survives tab throttling. Compass uses `deviceorientationabsolute` / `webkitCompassHeading`; with no sensor, show text ("The Oracle says: North-East") plus a distance band instead of exact meters.

**6.2 The Siren's Song (Web Audio, procedural, no files needed):** 2 detuned sine/triangle oscillators + low-gain filtered noise → lowpass BiquadFilter → GainNode, with a gentle LFO. Frontend Haversine on EVERY GPS update, independent of the 39 s UI refresh:
- `> 100 m`: silent
- `100 m → radius`: gain 0.05 → 1.0, frequency 220 → 880 Hz, filter cutoff and LFO rate rising on an ease-in curve
All changes via `setTargetAtTime`/`linearRampToValueAtTime` (no clicks). Volume slider and mute. Auto-resume on `visibilitychange` or suspended context with a "Tap to hear the Sirens" prompt. Short chime on capture. Ink-wave visual intensity indicator.

**6.3 Location → server:** emit every 7 s while visible. If movement < 5 m for 30 s, pause emits but send a heartbeat every 20 s.

**6.4 Resilience:** offline banner, auto-reconnect, queued last position, state restored from the server after refresh/crash, "permission revoked mid-game" handling, small payloads for weak networks.
